API reference

Overview

The Friendly ERP API is a small REST API over HTTPS. Every response is JSON. It exists to get data out of a workspace — into a dashboard, a warehouse, or a report.

This API is read-only. Apart from logging in, every endpoint below is a GET. There are no endpoints to create or update leads, bookings or users yet. We would rather tell you that here than have you find out halfway through an integration — see Not yet available.

Base URL

https://your-domain.example/api

Authentication

Log in once to exchange an email and password for a JSON Web Token, then send that token on every request. Tokens are valid for 24 hours. 

Authorization: Bearer <token>

The token carries your user and workspace identity. It is signed with HS256 and the algorithm is pinned on verification, so a token cannot be downgraded to none.

Which workspace?

If the same email exists in more than one workspace, the login is ambiguous and will be rejected. Pass tenantSlug to say which one you mean.

Tenant isolation

Your token determines your workspace, and you cannot read outside it. That boundary is enforced by PostgreSQL row-level security, not by the API code: each request runs inside a transaction that sets the tenant context, and the database filters every row against it.

This matters for a reason worth being blunt about: if the API had a bug, the database would still refuse to return another workspace's rows.

Permissions apply on top. GET /api/leads requires view_leads. If your user can only manage their own leads, the endpoint silently returns only leads assigned to you — the same rule the app itself uses.

Errors

Errors return a JSON body with an error string.

StatusMeaning
400Missing or malformed parameters.
401Missing, expired or invalid token. Also returned for a failed login.
403Authenticated, but your role lacks the permission.
404Not found — or in another workspace, which is indistinguishable by design.
429Rate limited. Back off and retry.
500Server error. Includes a correlationId.

A 500 never leaks internal detail. It returns a correlation id that matches the server log line: 

{
  "error": "Internal server error",
  "correlationId": "7f07ba33-4c1e-4a2b-9d5e-2f8c1b0a9e44"
}

Quote that id to support and the exact failure can be found.

Rate limits

ScopeLimit
POST /api/auth/login5 requests per minute, per IP
Everything else120 requests per minute, per IP

Exceeding a limit returns 429 with a Retry-After header.

Endpoints

GET /api/health

Liveness check. No authentication. Use it for uptime monitoring and after a deploy.

curl https://your-domain.example/api/health
{ "ok": true }
POST /api/auth/login

Exchange credentials for a token. No authentication required.

FieldTypeRequiredNotes
emailstringYesCase-insensitive.
passwordstringYesVerified with argon2id.
tenantSlugstringNoRequired only if the email exists in several workspaces.
 
curl -X POST https://your-domain.example/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"you@builder.com","password":"..."}'

200 — token plus the signed-in user and workspace.

{
  "token": "eyJhbGciOiJIUzI1NiIs...",
  "user":   { "id": "...", "name": "...", "email": "...", "role": "..." },
  "tenant": { "id": "...", "name": "...", "slug": "...", "plan": "Growth" }
}

401 — { "error": "Invalid email or password" }

The same message and the same response time are returned for an unknown email and a wrong password, so the endpoint cannot be used to discover which addresses have accounts.

403 — the workspace is suspended. This is returned only after the password is verified, so it tells a legitimate user what is wrong without leaking anything to a stranger.

GET /api/auth/me Auth

The signed-in user, their workspace, and their resolved permission list. Use it to render UI without hardcoding what each role can do.

curl https://your-domain.example/api/auth/me \
  -H "Authorization: Bearer $TOKEN"
{
  "user":        { "id": "...", "name": "...", "email": "...", "role": "sales_manager" },
  "tenant":      { "id": "...", "name": "...", "slug": "..." },
  "permissions": ["view_dashboard", "view_leads", "manage_leads", "..."]
}
GET /api/leads Auth

List leads in your workspace. Requires view_leads.

QueryTypeNotes
stagestringFilter by pipeline stage key, e.g. qualified.
assigned_touuidFilter by the assigned user.
searchstringMatches name, or phone. Phone matching ignores spaces, brackets and dashes, so 98765 43210 finds +91-98765-43210.
limitintegerPage size.
offsetintegerRows to skip.
 
curl "https://your-domain.example/api/leads?stage=qualified&limit=25" \
  -H "Authorization: Bearer $TOKEN"
{

Role-aware results. If your user has only manage_own_leads — a sales executive — this returns just the leads assigned to them. There is no parameter to override that.

403 — { "error": "Missing permission: view_leads" }

GET /api/leads/:id Auth

A single lead by id. Same shape as one entry above. Requires view_leads.

curl https://your-domain.example/api/leads/8a1f... \
  -H "Authorization: Bearer $TOKEN"

404 if the lead does not exist, is outside your workspace, or is not yours to see. All three are the same answer on purpose.

GET /api/meta/:entity Auth

The workspace's active definitions for an entity — its pipeline stages, form fields and list views. This is how the app avoids hardcoding anything: it renders from this JSON.

Read this before interpreting a lead's stage. Stages are defined per workspace, so a stage key you have never seen is normal. 

curl https://your-domain.example/api/meta/lead \
  -H "Authorization: Bearer $TOKEN"
{
  "pipeline": {
    "stages": [
      { "key": "new",       "label": "New",       "color": "#3b82f6", "order": 1 },
      { "key": "qualified", "label": "Qualified", "color": "#6366f1", "order": 3 },
      { "key": "booked",    "label": "Booked",    "color": "#10b981", "order": 6, "terminal": true }
    ],
    "_version": 1
  },
  "form": { "fields": [ ... ], "_version": 1 }
}

Not yet available

An API reference that lists endpoints which do not exist is worse than no reference. So, plainly — the following are not in the API today:

  • Any writes. No creating or updating leads, bookings, projects, units or users.
  • Bookings, payments and inventory. Not exposed. Available in the app and the workspace export.
  • Workspace administration. No API to create a workspace, invite users or change plans.
  • Webhooks. No outbound events. The app has an inbound lead-capture webhook for microsites and integrations, which is not part of this API.
  • Portal accounts. Buyer and channel-partner logins are a separate system and have no public API.

Need to move data out in bulk today? An admin can export the entire workspace as JSON from Platform Control. If you need a specific write endpoint, tell us which one — that is how this list gets shorter.
